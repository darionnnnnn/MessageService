## 視覺基準

- **色彩 token 取樣自 LINE 官方 App 實機截圖**（`chat.css` 的 `:root`）。聊天背景
  `--line-chat-bg: #8CABDC` 是 LINE 標誌藍紫——改版前的 `#8db2c4` 偏灰綠，一眼就不像。
- **只做亮色主題，不做深色模式**（改版時確認的範圍決定）。
- **相似度優先於原創**：底部列仿 LINE 輸入列但唯讀化（圖示灰化不可點、中央膠囊顯示同步狀態），
  遠看是 LINE、近看不會誤導使用者以為能發訊息。
- **標頭底色改過兩次**：改版時依手機版截圖做成與聊天區同色（透明感）→ 回饋二發現群組名浮在
  同色背景上缺乏分層，改成加深一階的藍 `#7B9BD2` → 第五輪對齊 LINE **桌面版**改為白底＋細分隔線
  （加深藍與背景只差一階，分界仍不明確）。桌面版與手機版的 LINE 標頭本來就長得不一樣。
- **泡泡尾巴在左上角**：頭貼是頂端對齊，尾巴貼底就指不到頭貼。尺寸用 `em` 跟著字級縮放，
  固定 px 會在放大字級後被圓角吃掉而看起來脫落。
- 截圖中有但**不做**（收錄端無對應資料）：回覆引用區塊、連結預覽卡片、頂部公告列。

## 字級系統

- **單一縮放係數全頁生效**：初版三檔字級只套在 `.bubble` 一個元素，其餘文字全是固定值，
  切字級幾乎沒感覺。改為聊天頁所有文字（不含頭貼/圖示等圖形元素）都用
  `calc(var(--chat-base-current) * <元素既有 rem> / 1.15rem)` 換算。
- **基準值 px 化**：設定頁的「字體大小」數值＝「中」檔泡泡文字的實際 px，小/大為相對係數
  （×0.87 / ×1.13）。px 是使用者指定的絕對值、跨裝置一致，這正是需求要的——
  代價是 `html` 14px→16px 的響應式基準不再影響聊天字級（手機嫌大自己調小）。
- **存 localStorage 不進 DB**：顯示偏好跟裝置螢幕走，每台各自記，`ViewerSettings` 免加欄位、零 migration。
- **變數掛在 `document.documentElement`**：設定改成 modal 後與聊天頁同頁，但 modal 在 DOM 上
  不是 `#chat-app` 的子節點，掛根元素兩邊才都吃得到（也讓調字級時背後聊天畫面即時預覽）。
  刻意不在樣式表宣告 `--font-base-px` 預設值——同元素上有宣告就贏過繼承，會讓 inline style 永遠蓋不掉。

## 匿名代號系統

需求核心：匿名下**仍要能分辨是不同人在發言**（同一人永遠是同一隻小熊），只是認不出真實身分。

- **伺服器端裁決**：非 `Original` 模式時 `PictureUrl` 一律回 null，不是靠前端不渲染——
  URL 本身就是身分線索。名稱與圖示的唯一事實來源都在伺服器，兩者才不會對不上。
- **24 款動植物圖示，排除口語帶貶義者**：豬/狗/老鼠/蛇/雞/烏龜/驢/狐狸/猴一律不用
  （含「鼠」字的松鼠也避開），嚴肅環境的用字審查。
- **DB 持久化指派表**（`AnonymousIdentities`，GroupId+UserId 複合主鍵）。
  - 為何不用純雜湊 `hash(userId) % 24`：24 款圖示配 5~20 人幾乎必撞名（生日悖論），
    撞了就違反「看得出是不同人」。
  - 為何不用「雜湊＋成員清單排序推序號」（免 DB 的替代案）：成員增減會讓既有人的序號位移
    （小熊 2 變小熊 3），回頭翻舊訊息時代號就對不上，嚴肅環境的紀錄必須可追溯。
  - 併發防護：GET 訊息端點觸發冪等指派，撞複合主鍵就 catch 後重讀既有那筆。
- **已知限制（接受不修）**：兩個併發請求各為「不同的」新成員指派、又剛好雜湊到同一圖示時，
  理論上可能產生兩個「小熊」。需在毫秒級窗口內首次載入同群組的不同新成員才會發生，
  單一使用者＋IP 白名單的工具可接受。開兩個分頁載入同批成員不受影響（順序與雜湊相同，Label 一致）。
- **代號一經指派永久有效**（切回 Original 再切回匿名仍是同一組）：這是特性不是 bug。
  要重洗代號得另做管理功能。
- 實作偏差：規劃寫 SVG sprite，實際用 emoji 字元圖示（沿用 chat.js 既有的 📄 慣例），更簡單且同樣零外部依賴。

## 遮蔽一致性（嚴肅環境的核心設計）

- **側欄預覽也要套遮蔽**：不然關鍵字遮蔽在側欄上被繞過。
- **搜尋不能變成遮蔽的後門**：SQL 先用原文 LIKE 撈候選，記憶體內套遮蔽後**重新驗證**
  遮蔽後文字仍含關鍵字才算命中——被規則遮掉的詞（如「密碼」）搜不到、摘要也是遮蔽後文字。
- **搜尋的名稱比對走當前顯示模式解析後的名稱**；`Anonymous` 模式查既有指派但**只讀不指派**——
  沒被指派過的成員名稱搜不到是正確行為，指派只發生在訊息視窗端點。
- **只搜文字訊息的 Text 欄**：媒體訊息無文字可搜，檔名不搜（檔名未經遮蔽管線）。
- 所有訊息內容（含搜尋高亮、linkify）一律用 DOM 節點組裝，不走 `innerHTML`——訊息是外部輸入。

## 輪詢與即時性

- **訊息 3 秒、側欄 10 秒**：側欄資訊（新群組/預覽/排序）不需要 3 秒級即時性，
  而 `/api/groups` 一次要跑好幾個查詢，沒必要同頻。
- **側欄輪詢失敗靜默、不回報連線狀態**：連線狀態由訊息輪詢負責，兩條各自回報會在
  「一好一壞」的交錯下讓橫幅閃爍。例外：還沒選到任何群組時（空庫啟動）它是唯一對外請求，才由它回報。
- **歷史檢視（搜尋跳轉後）暫停把新訊息接到視窗尾端**：視窗錨定在過去某時間點，
  接上去會出現時間斷層；Pending 內容狀態輪詢照常（與是否即時畫面無關）。
- **刻意不做——目前群組的預覽即時更新**：要在前端複製 type→label 與遮蔽邏輯才能就地組預覽，
  重複邏輯不值得，10 秒內側欄自然更新。
- **刻意不做——聊天標頭群組名/成員數即時刷新**：每輪重繪會讓頭貼 `<img>` 每 10 秒重載造成閃爍。

## 側欄寬度與收合（第五輪）

- **兩段式收合**：全寬 → 72px 頭貼窄欄 → 完全隱藏。中間那段窄欄是 LINE 桌面版實際的壓縮清單行為，
  比「只有顯示/隱藏」更貼近參考對象。
- **吸附遲滯 140/180**：拖進與拖出用不同門檻，避免在臨界點抖動。
- **窄欄的 72px 不覆蓋寬度記憶**：回到展開時沿用上次自訂的寬度。
- **rail 模式的 tooltip 用原生 `title`**：自製 tooltip 會被群組列表的 `overflow-y:auto` 裁掉。
- **三態 CSS 全包在桌面斷點內**：手機版是單欄全螢幕切換，桌面狀態不該外洩；
  手機版 `.sidebar` 的 `position:absolute; width:100%` 也天然蓋掉桌面寬度。
- **桌面斷點寫成 `not all and (max-width: 768px)`，不是 `min-width: 769px`**：
  體檢時實測發現，顯示縮放 125%／瀏覽器縮放會產生 768.5px 這種分數視埠寬，
  兩個查詢都不匹配——收合鈕看得見卻按不動、分隔線無法拖曳。寫成手機斷點的精確補集才沒有縫隙。
  日後若調整手機斷點數值，兩處要一起改。
- **收合鈕/分隔線放在 `#group-list` 之外**：群組列表每 10 秒 `innerHTML` 全量重建，放進去會被清掉。

## 未讀數 badge（第一輪說不做 → 第五輪做了）

回饋一列為「另案」的理由是當時架構沒有「已讀」概念。第五輪的解法：

- **已讀基準存前端、數字由後端算**：唯讀檢視器沒有登入，已讀本來就是「每台裝置各自」的概念
  （localStorage `chat-read-state`），但計數必須靠 DB。折衷成 `GET /api/groups?read=群組:Id,...`。
- **上限 100 在 SQL 端截斷**（顯示 99+）：不必真的數完一個很久沒看的群組累積的成千上萬則。
- **本裝置首見的群組直接視為已讀**：否則初次開啟整排都是 99+。
- **開著的群組視為已讀**（LINE 慣例）：切入群組、新訊息接進畫面時都推進基準；搜尋跳轉的歷史檢視不推進。
- **對比度登記例外**：badge 用 LINE 正宗綠底白字，白字對 `#06C755` 約 2.3:1 未達 4.5:1。
  品牌識別優先，且 badge 另有位置/形狀作為冗餘指標。要嚴格達標改 `#0E873F`（4.6:1）一行即可。

## 其他決策

- **`--focus-ring` 必須與 `--sidebar-active` 分開**：選取色從淡藍改灰時，若共用同一個 token，
  輸入框的鍵盤焦點提示也會跟著變灰而看不清楚。
- ~~**泡泡寬度上限 `min(75%, 34rem)`**~~（第六輪推翻）：原本理由是 `rem` 以根字級為基準、
  不隨聊天字級縮放，放大字級時上限不動、自然多換行。**但絕對上限在寬螢幕會反過來咬人**——
  34rem＝544px，在 1920px 螢幕上只吃掉聊天面板的三分之一，右側固定空一大塊。
  改用比例上限 `--bubble-max-width`：桌面 2/3、手機 75%（2/3 在 375px 只剩 250px，太窄），
  設定可勾選全版面（100%）。比例值同樣不隨聊天字級縮放，原本的好處沒有損失。
- **加寬只給文字，媒體另立絕對上限**：泡泡放寬後 `.msg-video`/`.msg-audio` 會跟著長大
  （全版面模式下變成整排寬的播放器），所以加 `min(100%, 30rem)`。圖片有 `max-height: 16rem`
  等比縮放下寬度自然受限、貼圖是固定尺寸，兩者都不必動。
- **全版面設定沿用 localStorage、不進 DB**：與字級同一類的顯示偏好，跟裝置螢幕走。
  套用方式是在 `documentElement` 上設 inline CSS 變數——**未勾選時必須 `removeProperty`
  而不是設回預設值**，否則會把媒體查詢決定的手機版 75% 一起鎖死。
- **「載入更早」常駐、「沒有更早的訊息」只在頂部顯示**：前者是操作入口，藏起來影響可發現性；
  後者是純狀態告知，在畫面中間看到很突兀。
- **圖片燈箱的縮放判斷要三重保險**：`onload` + `decode()` + 雙 `requestAnimationFrame`。
  連續開同一張圖時 src 沒變，各家瀏覽器對 onload 該不該再觸發的語意實測並不一致；
  且必須先 `show()` 讓 modal 進版面才量得到 `clientWidth`（隱藏時是 0×0）。
- **設定改 modal 並 lazy init**：首次 `shown.bs.modal` 才載入資料，聊天頁一開不會多打一輪設定 API。
  失敗時要放掉 `dataLoaded` 旗標讓下次重開重試（體檢揪出的 bug：瞬斷後永遠空白到重整頁面）。
- **`/Home/Settings` 頁面已退場**：設定抽成 partial 由聊天頁引入，避免同一份表單有兩個渲染路徑各自漂移。
- **貼圖歷史資料無法回溯**：改版前收到的貼圖沒有 `StickerId`（LINE 不提供舊訊息查詢），
  一律 fallback 回「(貼圖)」文字。貼圖不裝白色泡泡——LINE 是浮貼在背景上。
- **前端無自動化測試**：專案無 JS 測試框架，UI 行為一律人工／瀏覽器端到端驗證。
